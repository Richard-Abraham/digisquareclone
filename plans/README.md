Two defects were found in review and fixed (commits `987b722`, `e660a76`). Both originated in
the plan, not the executor:

1. **The follow-up update dropped `state`.** `create_issue_atomic` returns
   `to_jsonb(i.*) || jsonb_build_object('state', …)`, not a bare issues row
   (`0010_fix_issue_arrays.sql:99-104`). Re-selecting without `state:states(*)` meant every
   client-attributed task came back stateless, and `dashboard/page.tsx:147`
   (`i.state?.group_name || "backlog"`) put the new card in Backlog until refresh. Fixed by
   adding the embed; the plan's Step 4 now explains why it is mandatory.
2. **`ilike` treated client names as wildcard patterns.** `%` and `_` in a create-or-reuse
   lookup could match a *different* client and silently attribute work to the wrong customer,
   while the DB uniqueness index on `lower(name)` matches exactly. Fixed with
   `escapeLikePattern` in `src/lib/tasks.ts` at both call sites, with tests.

Two corrections to the plan's own instructions, learned during execution:

- **`npm run build` is not a usable gate.** It compiles and type-checks, then fails in Next's
  "Collecting page data" phase on `Invalid environment variables: SUPABASE_URL /
  SUPABASE_SERVICE_KEY` — `src/lib/env.ts` validates at import time and `/api/auth/login`
  pulls it in. Reproduces on an unmodified checkout. All plans now specify
  `npx tsc --noEmit -p tsconfig.json`.
- A review criterion reading "every `ilike("name"` hit is wrapped in `escapeLikePattern`"
  was wrong: `issues/route.ts:63` is the issue-title substring search and must keep its
  `%…%` wildcards. The executor correctly refused to comply and flagged it.

- `0010` is now recorded as applied whether or not it truly was, so it will never be applied

## Decisions already made (do not re-litigate)

These were settled with the operator before the plans were written:

- **A client request is an issue**, not a separate entity. A standalone `client_requests`
  table with a "convert to issue" step was considered and rejected: it duplicates status,
  assignee, filtering and permission plumbing for no gain.
- **Vault access is a per-credential access list**, not role-based visibility. Managers see
  and manage everything; other members see only what they were explicitly granted.
- **Credential files go in a private Supabase Storage bucket** and are served through
  60-second signed URLs after an access check. Application-level encryption at rest was
  considered and deferred — the limitation is documented in plan 004 and surfaced in its
  UI.
- **The standup report is delivered as browser print-to-PDF** from a print-optimised page,
  plus a CSV export. A server-side `pdf-lib` route is specified as an appendix in plan 005
  and is to be built only if the operator asks for a real streamed PDF file.

## Known constraints every executor must respect

- **The core tables** — `workspaces`, `workspace_members`, `projects`, `project_members`,
  `issues`, `states`, `profiles` — are **not** in `supabase/migrations/`. They exist only in
  the hosted Supabase project, so the schema is not reproducible from this repo alone.
  Verify column assumptions against the live database rather than the migration folder.
- **Every API route uses the service-role client (`getAdmin()`), which bypasses RLS.**
  Authorization lives entirely in application code, via the resolvers in `src/lib/access.ts`.
  There is no database-level backstop; a missed check is a data leak.
- **Migrations are append-only and idempotent.** Never edit an existing migration file.
  Next free number is `0011`.
- `npx tsc --noEmit -p tsconfig.json` is the typecheck gate — there is no lint script and no
  ESLint config. **`npm run build` cannot complete without a `.env`**: it compiles and
  type-checks, then fails in Next's "Collecting page data" phase on
  `Invalid environment variables: SUPABASE_URL / SUPABASE_SERVICE_KEY`. Reproduces on an
  unmodified checkout — it is not a symptom of your change.
- **There is no `.env` in this repo**, so the app cannot boot locally and no executor can run
  browser or dev-server verification. `npx tsc --noEmit` + `npm test` are the only usable gates;
  runtime checks must be reported as DEFERRED, never as passing.
- **Three modules look authoritative and are dead or orphaned**: `src/lib/route.ts`
  (`createHandler` — zero callers), `src/types/index.ts` (one importer), and
  `src/lib/supabase-browser.ts` (zero importers). `src/lib/validation.ts` is half-adopted —
  its `issueCreateSchema` / `projectCreateSchema` / `tagCreateSchema` are never imported.
  Do not build on any of these without a deliberate migration.
- **`create_issue_atomic` may have two overloads on the live database.** `0009` defined it
  with `uuid[]` params, `0010` redefined it with `text[]` and no `drop function`. Verify with
  `select oid::regprocedure from pg_proc where proname = 'create_issue_atomic';` — more than
  one row needs a cleanup migration before anything touches issue creation.
